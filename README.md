# Что делать 

Поделим общие работы примерно поровну, в идеале 4 человека, каждый ответсвенен только за свой перечень работ.

Чтобы минимизировать количество исправлений друг у друга предлагаю такую последовательность шагов по каждой лабе:

1) Берем свежий main: `git switch main` -> `git pull`.
2) Делаем свою именную ветку, например `leontevskii`. В ней все свои работы.
3) Выполнение -> коммит -> пуш в свою ветку.
4) Открываем PR (пулл реквест) на GitHub, когда лаба готова.
5) Сдача -> правки (если есть) -> коммит и пуш в свою ветку, PR сам обновится.
6) Подтверждение что работа выполнена -> пишем в PR или отдельным файлом, о чем спрашивали на защите.
7) Мержим PR обычным merge (не squash), ветку не удаляем — в ней делаем следующие лабы.
8) Перед новой лабой подтягиваем main к себе: `git pull` в main, потом `git merge main` в своей ветке.

В main напрямую не пушим, туда все попадает только через пул реквест. Ветка на человека, а не на лабу: у каждого своя зона ответственности, работы между ветками не пересекаются, поэтому конфликтов почти нет. Обычный merge оставляем, чтобы ветку можно было продолжать после мержа.


# Принципы:

- Автор работы всегда сдает ее первым, дальше очередность не важна.
- Давайте будем описывать, как проходила защита, чтобы без сюрпризов.
- Отчеты давайте писать в md или txt файлы, чтобы каждый свой отчет форматировал самостоятельно.
- Смысл репы — за неделю собрать по одной отправной точке (авторской версии) на каждую из 16 общих лаб.
- Свои лабы и отчет кладем по папкам `src/<предмет>/<лаба>/`.
- В репе лежит только авторские версии — отчет и артефакты. Это шаблоны.
- Остальные берут шаблон, допиливают под себя локально и свою версию в репу не коммитят.
- Чужие отчеты в репе не правим, свои правки под себя держим только локально.
- Ветку после мержа не удаляем, продолжаем в ней следующие свои лабы.
